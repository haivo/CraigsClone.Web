Tuples, not `City`/`Category` instances: a static entity object would get its `Id` set the first time it's inserted and then be shared by every later context, which is a classic EF bug. The seeder creates fresh entities from the tuples each run.

Checking by slug is what makes it safe to run every startup.

## Tests

**Unit** — `Unit/Data/DbSeederDataTests.cs`, reading the static lists only:

- 6 cities, 22 categories.
- All city slugs are unique; all category slugs are unique.
- No slug is one of `post`, `search`, `listing`, `error`.
- Every slug matches `^[a-z0-9-]+$` (lowercase, URL-safe).
- Every `CategoryGroup` value has at least one category.

**Integration** — `Integration/Data/DbSeederTests.cs`, `[Collection("postgres")]`:

- Call `SeedAsync` twice. Afterwards exactly 6 cities and 22 categories with *seeded* slugs exist. Count by slug, not the whole table: other tests insert cities with random slugs into the same database.
- Note: the fixture will itself call `SeedAsync` from M1.5 on, so this test's first call is really the second run. That's fine; the assertion is the same.
- Raw SQL reads the `Group` column for `furniture` and gets the text `ForSale`, proving the string conversion from M1.2 is what's on disk.
